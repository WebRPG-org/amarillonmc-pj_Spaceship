# RPG Maker MV/MZ 地图设计

把地图做成有用途、可辨认、可游玩的场所。保留项目已有的图块语言和游戏机制；把空间设计、图块实现、视觉复核和运行验证分别完成。以用户要求和项目事实决定风格，不把教程中的个人偏好当作硬规则。

## 按任务读取资料

- 开始设计前，读取 [design-playbook.md](references/design-playbook.md)：功能、尺度、素材语法、场景类型与整批差异。
- 记录方案、评审地图时，读取 [design-contracts.md](references/design-contracts.md)：设计卡、Sample 观察表、批次对照与验收记录。
- 接触工程文件、图块 ID、图层或试玩时，读取 [engine-workflow.md](references/engine-workflow.md)。必须先判断 MV/MZ 和项目插件差异。
- 解释原理、需要深入教程时，读取 [sources.md](references/sources.md)。其中区分一手来源与本 Skill 的综合设计建议；日常任务无需重读所有网页。
- 需要清点工程时，运行 `python3 <skill目录>/scripts/inspect_project.py <项目目录>`。可加 `--maps 31 32 33`。Windows 可用 `python`。该脚本只读文件，不进行寻路、碰撞验证或审美评分。

## 1. 确认任务边界并读取项目

1. 区分新建、重绘和只评审。用户要求制作时继续完成制作；只评审时不修改工程。
2. 读取项目说明、相关 AGENTS.md、目标地图、相邻地图、相关 Sample、图块集配置、事件和插件。确认编辑源工程位置，不把发布包当作完整源工程。
3. 记录需保留的机制：地图和事件 ID、事件页与条件、出入口、公共事件引用、箱子/敌人/机关、区域用途、开关、自开关、移动路线及已有平衡要求。重绘需要移动事件时保留身份与含义，并同步所有已知坐标引用。
4. 默认复用现有素材。不要因为新布局难画就覆盖共享图块表、批量改通行标记、加插件或另造奖励。素材调整已被授权时，可另建有清晰映射的变体；先检查所有受影响地图。
5. 少量未知项用有依据的假设推进。缺素材图、Sample 或可运行工程时，仍完成能够完成的分析/方案，并明确无法核实的部分。不能声称看过没有打开的图片或运行过不存在的工程。

**产出：** 简短任务约束与实际可用证据。复用项目已有文档位置；小改动可直接在工作记录中写明，不为每张小图制造一套文档。

## 2. 把 Sample 拆成素材语法

1. 同时打开图块 PNG 和相关 Sample 的实际地图画面；只有 JSON 和文件名不足以识别家具用途。若已有渲染器，优先用它生成预览。
2. 挑选少量有代表性的 Sample，覆盖本次会用到的墙体、地面、完整家具、转角、高差或自然边缘；通常两三张足够，按素材复杂度调整。
3. 按观察表记录组合：来源文件/槽位、已核实的 tile ID 或图块坐标、物件完整占地、锚点、朝向、图层、墙地连接、遮挡、通行/交互语义，以及 Sample 中的对应位置。
4. 区分可以复用的局部组合和需要重设计的整体布局。学习床的拼接与落地位置，不继承卧室必须位于整图左上角；学习崖壁的连接，不继承所有路线都绕同一块中心障碍。
5. 不确定图块语义时，在临时测试地图中组合并查看。不要只凭相邻 ID 猜测床头、柜门、池边、墙顶或玻璃的用途。整件放置多格物件，检查是否缺角、悬空或被上层擦除。

**产出：** 可复用的素材组合与项目风格约定。不要把用户素材或 Sample 复制进通用 Skill。

## 3. 先设计场所，再决定轮廓

为每张目标图填写简短设计卡：

- 场所用途与形成原因；玩家本次要完成的事情。
- 入口、出口、必须可达的交互点；既有条件改变后可通行关系如何变化。
- 功能区及其相邻关系；主路线、可选路径、必要回返。
- 主视觉对象、入口可见信息、关键转向后看到什么。
- 尺度依据：实际视口、角色移动方式、家具占地和事件演出所需空间。
- 与邻接/同批地图的差异；必须保持一致的风格。

先画“区域—通道—门”的关系，不以 U/L/S/O 等字母代替设计。仅在骨架确需重做或方向不明确时比较少量候选；选择最符合任务的方案并自主继续，不把每个草案都变成用户审批。

### 多地图任务的前置检查

先填整批对照表，再精修单张地图。比较三件不同的事：

1. **空间组织：** 主要区域、连通关系、入口出口、分岔/汇合和回返。
2. **视觉组织：** 大块面、轮廓、开阔/收紧、主对象及空白分布。
3. **玩家体验：** 选择、信息揭示、用途和行动节奏。

如果只是换地板、换家具、旋转或镜像同一个通用户型，应在粗布局阶段重做缺乏理由的重复。图结构同构也不自动失败：多张线性剧情地图可通过场所组织和屏幕节奏形成合理差异。

**不要禁止 U 形、对称、直线、矩形、死路或留白；不要要求每张图必须有岔路或环路。** 医院走廊、重复客房、泳池围边、仪式中轴与真实折返可能正需要这些结构。用项目事实解释重复，不以“为了多样性”破坏功能。

## 4. 先做可验证的粗布局

1. 先落地面、墙体/崖体、主要障碍、入口出口和必要事件占地；暂不散放装饰。
2. 用项目实际尺度检查可走空间。计入门前落脚、家具使用侧、NPC 占位、巡逻、明雷回避、队伍/剧情移动和转场落点；不要只用单点主角的静态通路代替所有需求。
3. 检查路径有没有目的，绕行是否带来场所功能、视野变化或已有玩法。纯粹延长行走而无作用时，缩短路线或缩小空间。
4. 批量制图先完成一两张在用途上不同的代表图，核实素材拼接、尺度和渲染流程后再展开其余地图；不等到九张都装饰完才发现共享了错误骨架。
5. 实际打开粗图预览，修正空间问题后再细化。若只有框图，标记为布局草案，不称为游戏成图。

## 5. 从大到小铺设图块

按下列依赖顺序工作；允许场所需要的迭代：

1. **空间与高差：** 确定墙高、平台、崖面、门洞和楼梯连接。
2. **主要用途：** 放完整的大型物件/家具组、主地标与公共/私有区域边界。
3. **交通与交互：** 留实际可用的走道、操作面、视线和演出空间。
4. **材料与边缘：** 调整地面过渡、转角、自动图块、遮挡和阴影。
5. **局部生活痕迹：** 围绕用途摆成物件组；让疏密有区域性，保留有作用的空地。

先解决房间尺度和功能，后处理装饰。不可用随机撒花草、箱子、灯、售货机填补骨架不足；不可用阴影、雾、泛光或视差图片遮盖拼接错误。已有风格需要这些效果时，在基础地图成立后加入并验证。

## 6. 分开完成视觉、整批与运行检查

读取验收记录模板，实际保留以下证据；位置重合可合并，不机械凑截图数量。

- **全图预览：** 看轮廓、功能区、主次关系、无意义空地与建筑逻辑。
- **玩家视口：** 使用项目真实分辨率/相机，在入口、关键交互或选择点、主要地标、出口附近查看；带上真实角色与必要事件。检查转向前后和遮挡，不只看全图缩略图。
- **整批对照：** 统一格子比例或明确标注缩放比例，保留各图真实宽高比；检查用途不同的地图是否仍是同一户型和同一观看节奏。
- **运行验证：** 检查入口到必达点、事件触发、返回/转场、既有机关状态和关键移动路线。对未知插件/脚本行为保留待实测项。

用项目运行时/编辑器的真实渲染作为视觉依据。近似拼图不能证明自动图块、动画、星标遮挡、桌面边缘或插件效果正确。检查 JSON 的脚本不能证明“已试玩”。不能用自动计算的装饰密度、环数或相似度代替审美结论。

每个问题记录具体地图、区域/坐标、画面证据、影响和修改。按“布局 → 主要物件 → 图块接缝/遮挡 → 细节”处理；修改后复核受影响画面和行为。证据不足时报告“静态已查、实机待查”等真实状态，不自行补一个通过分数。

## 7. 交付

- 交付实际修改的工程文件或用户要求的评审结果，说明每张图的空间特点与修改原因。
- 附能说明结果的全图、关键视口或整批对照，沿用项目的输出约定。
- 简述保留的机制、完成的验证和具体未验证项；没有工程或渲染条件时清楚说明成果层级。
- 核对差异，仅保留本次目标内的修改。满足任务且没有具体遗留问题后停止额外装饰和泛化测试。
