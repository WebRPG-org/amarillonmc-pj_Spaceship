## 读取工程与检查工具

先查源工程根目录的 `data/`、`img/tilesets/`、`js/`。部分 MV 发布结构位于 `www/`；能找到发布数据不代表可以完整重建源工程，也不代表已取得编辑授权。

重点读取：

| 文件 | 本任务用途 |
| --- | --- |
| `System.json` | 项目配置、起始位置、可能的画面/图块尺寸信息 |
| `MapInfos.json` | 地图编号、名称与组织结构 |
| `MapNNN.json` | 尺寸、图块数据、事件、图块集、区域与地图属性 |
| `Tilesets.json` | 槽位到素材文件的对应关系，以及 flags、模式等配置 |
| 相关 Sample 的地图与图块配置 | 核实多格组合、自动图块边缘、遮挡与素材用法 |
| `js/rpg_*.js` 或 `js/rmmz_*.js` | 当前项目使用的 MV/MZ 核心实现 |
| `js/plugins.js` 与相关插件源码 | 判断相机、通行、区域、图层或地图格式是否被改写 |

在 Skill 目录之外运行只读清点工具：

```bash
python3 <skill目录>/scripts/inspect_project.py "<项目目录>"
python3 <skill目录>/scripts/inspect_project.py "<项目目录>" --maps 31 32
```

Windows 可改用 `python`。需要 Python 3.8+，只使用标准库。JSON 报告写到 stdout；需要保存时重定向到项目约定的审查目录，不要覆盖工程 JSON。

退出码：`0` 表示未发现本工具覆盖的静态错误，`1` 表示存在已报告错误，`2` 表示命令行参数错误。`--maps` 只限制地图/直接传送的详细输出，摘要与错误仍覆盖整个工程。

工具会清点图块集、远景和事件图像的静态文件引用，识别常见 PNG 与加密图像候选；检查地图尺寸/平面、事件坐标和地图事件中的直接指定传送。它不会执行 JavaScript、解密图片、解析所有公共事件、运行插件、验证实际图像内容、寻路或打审美分。素材候选缺失等判断基于标准加载约定；有自定义资源加载器时要人工核实。

## 图块和图层

### 不混淆编辑器层与数据平面

普通 MV/MZ 地图数据通常包含六个平面：

| 零起始 z | 通常含义 |
| --- | --- |
| 0、1、2、3 | 四个图块数据平面 |
| 4 | 阴影位数据 |
| 5 | Region ID 数据 |

常见扁平索引为 `(z * height + y) * width + x`，数组长度通常是 `width * height * 6`。不要把第 4、5 平面当成普通素材 ID，也不要把整张地图压成一个 tile 数组而丢掉上层、阴影或区域。

MV 原生编辑器主要按自动规则管理上下层，B–E 可叠两个上层图块；MZ 增加四层的手动选择。编辑器按钮的名称不能直接代替数据结构说明。两者的自动绘制、显示优先级与插件效果都需分别核实。

### 识别自动图块与完整物件

- A1–A4 含自动图块；A5 与 B–E 的组织不同。按真实槽位、图片尺寸和运行时映射识别，不把所有图片统一按普通 48px 方格编号。48px 是常见默认值，项目可能使用其他尺寸或插件。
- 自动图块 ID 包含已选定的形状信息。直接写 JSON 时，不要指望加载地图会像编辑器画笔一样自动修复所有相邻边缘；使用经过核实的形状映射、已验证的项目工具或编辑器操作。
- 对水边、瀑布、墙面、屋顶、桌面等不同类别单独处理；不要把一套邻接规则泛用到所有 A 图块。
- 编辑器中的 Shift 绘制/取样可控制自动连接。代码实现需核实对应的最终图块与邻域效果，不能将“使用 Shift”当成一个未实现的 JSON 字段。
- B–E 物件可能占多个格子。按 Sample 学会完整组合；同图层的新物件可能覆盖旧物件，不能仅以目标位置已有合法 tile ID 判定画面正确。
- 素材表位置会影响 ID 与 flag 对应。重排素材文件后必须重审对应映射；不要只移动 PNG 中的家具而保留旧地图的错误引用。

## 实际渲染与玩家视口

优先使用项目现有的编辑器导出、游戏截图、预览工具或测试启动方式。可用自动化工具时，复用该项目实际的 Tilemap、PIXI 与图块配置，不默认下载另一版引擎或临时加入视差插件。

若要实现辅助渲染：

1. 从项目运行时读取 tileWidth/tileHeight、画面尺寸与相机配置；MV/MZ 同名属性也可能被插件改变。
2. 使用实际 tilesetNames、flags 和图块数据，正确处理自动图块四分片、动画、阴影、桌面边缘和上下层。
3. 先把相关 Sample 用同一渲染路径输出，和编辑器/实机样本对照。若没有对照条件，标记为近似预览，不声称已等价。
4. 全图预览用于布局检查；玩家视口必须保留实际缩放、角色、重要事件与遮挡关系。
5. 保持截图的真实宽高比。整批对照注明缩放比例，避免把不同尺寸地图全部拉成同一方形而掩盖尺度问题。

图像生成结果、手绘示意图、彩色矩形平面图都不是引擎成图。它们可以表达概念，但不能作为自动图块或遮挡验收证据。

没有可运行条件时仍可检查素材和静态预览，明确具体未覆盖项。不要以缺乏实机环境为由反复要求用户审批已经能够完成的规划，也不要把未测状态填成通过。

## 通行与事件

四方向可达性不只是“这一格的 flag 是否为可走”。查看项目中的 `Game_Map.checkPassage`、`Game_CharacterBase.canPass` 及其插件覆盖；考虑出发方向、目标反向、图层顺序、星标跳过逻辑、事件图块、事件碰撞、Through、循环地图与区域限制。

`☆` 是显示/通行判定中的特殊标记，不等于无条件可走；下面的阻挡层仍可能生效。桥梁上下通行、平台跨层和区域插件也不能从一张平面网格中自行推断。

进行路径检查时：

- 使用真实出生/转场落点到所有当前必达点的路径。
- 若已有机制含锁门、开关或多页事件，分别检查相关状态。不要只测试一个全开或全关的理想状态。
- 检查与 NPC 对话、柜台互动、开箱和门触发的位置；站到事件自身格子不一定是正确的可达条件。
- 核实关键事件的移动路线及队伍站位；单角色路径成立不代表演出不会卡住。
- 明雷回避只在原玩法允许/要求时检查，不为所有地图强加绕怪通道。

区域—通道关系图服务于设计讨论；逐格寻路服务于行为验证。开放广场产生的大量网格小环，不是应该记录的“探索回路数”。

## 修改和交付

保持未知字段、note、BGM、遇敌设置、滚动方式、远景和事件页等非目标内容。缩放/平移地图前先检查所有已知坐标依赖：直接传送、Set Event Location、移动路线、公共事件、脚本、插件指令、起始位置及邻接地图回程。

保留事件 ID 与地图 ID，防止自开关、存档状态和其他地图引用串位。用户只要求地图美化时，不要重新分配现有宝箱内容、敌人数量或任务条件。需要改变坐标的重绘并不等于只能给旧布局加装饰：可以移动，但要同步引用并验证原有功能。

使用项目已有的隔离修改与备份方式。核对最终 diff，只提交本次相关文件；不要让新生的审查图片、临时测试地图或运行脚本覆盖正式地图。

在交付说明中分别列出数据检查、静态视觉、整批设计和实机行为。只做过合成数据测试的工具，不得被描述成已在用户游戏中验证。
