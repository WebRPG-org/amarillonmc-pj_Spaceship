# 第二阶段原型与测试素材方案

原始规划日期：2026 年 10 月 6 日，UTC。本文保留阶段开始前的设计与验收目标；10 月 11 日的用户定案与实际实现见 [第二阶段实施记录](2026-10-11-playable-instances.md)。下文早期建议中的掉线退赛、钥匙消耗和第二出口路线已被新规则取代，不能作为当前行为说明。

下一版的目标是让少量玩家从进入、探索搜刮、战斗与合成，一直玩到禁区推进、死亡或逃离以及最终结算，完整完成一局。当前仓库的地图与美术足以支持这项验证，无需先购买素材、重画大地图或建立新编辑器。

第一阶段记录见[当日归档](2026-10-06-project-revival.md)。当前已有能力与启动方式见 [engine/README.md](../engine/README.md)。本方案中的新增规则不能当作现有代码功能。

## 原型规模与完成标准

建议采用 4–8 人、15–20 分钟、6 个互通区域的测试局。先用 2 名真人验证关键交互，再用少量机器人补足测试角色。这是验收目标，不是对当前性能或最终 MMORPG 容量的承诺。

一局的基本流程为：准备与倒计时 → 探索与搜刮 → 战斗或绕行 → 合成与触发世界事件 → 禁区推进 → 两种逃生路线之一或失败 → 结算与下一局。

完成标准是：不依赖开发传送、管理员补发物品或手工修改变量，就能反复完成整局；第二局不会继承上一局的掉落、箱子、机关或未完成动作。

建议先采用以下可调整规则：

| 项目 | 本轮建议 |
| --- | --- |
| 背包与成长 | 账号保留，测试局内资源独立；新局不带入上一局测试物资。局外成长以后另定 |
| 死亡 | 正式局中不可随意重生，随身物品按确定的规则形成可搜刮遗物 |
| 掉线 | 暂按 60 秒重连宽限期设计，角色留场且继续承受战斗和禁区伤害；超时记为退赛 |
| 普通路线 | 找到指定钥匙或通行物，满足出口条件后撤离 |
| 特殊路线 | 搜集两类零件，合成并启动共享装置，开放另一出口并产生不同结局 |
| 个人与全局结算 | 逃离者先确定个人结果，未离场者继续；所有人结束或局时限到达后，整局只结算一次 |
| 服务意外重启 | 第二阶段先保证该局明确中止、不重复结算；完整恢复所有弹道、敌人与事件执行位置留到后续 |

这些规则可以改，但必须明确写入场景配置和测试预期，不能由客户端是否在线、某个菜单是否打开或旧变量偶然取值来决定。

## 第二阶段实施内容

### 对局身份与多人事件作用域

先将账号身份、局内角色状态和对局状态分开。当前 [schema.sql](../engine/server/schema.sql) 只有玩家、操作去重和世界掉落等基础表，掉落按地图编号查询；[world.mjs](../engine/server/world.mjs) 的地图实例也只按地图编号区分。这还不能让两局安全地使用同一张地图。

需要增加对局、参与者、局内角色、共享容器和结算记录等概念。地图、实体、掉落、广播和操作去重都必须带上对局身份。验收时同时运行两局、引用相同源地图，验证人物、箱子、怪物、开关与掉落互不影响。

事件首先明确两种作用域：个人和本局共享。个人对话与任务进度不影响其他人；共享门、怪物、机关和容器由本局服务端统一拥有状态。队伍与跨局永久世界状态可以稍后扩展。

当前个人条件页与共享敌人身份存在语义缺口：画面可按个人开关切页，但敌人 AI 身份在创建时确定。下一版必须统一共享敌人的存在性、页面、碰撞、HP 和 AI，防止某人看不到的实体仍能攻击他。

### 搜刮与可结算的资源循环

在现有拾取和配方基础上加入搜刮点、共享容器、搜索耗时、打开状态和局内唯一资源。两人同时取走箱中最后一件物品时，只允许一人成功；容器库存和玩家库存必须在同一事务中修改。

先选 6–10 种道具、2–3 条配方和两类武器验证完整流程。原数据库的数量与恢复强度是旧测试配置，需要为这一局单独配置数值，不能直接认为已经平衡。保留原条目，用场景配置引用 ID 并覆盖测试数值，避免破坏旧项目。

正式局关闭随意传送、补满物资和死亡重生按钮。独立功能测试房可以继续使用这些工具。

### 足够验证追杀与逃离的战斗

先把近战、远程弹道、恢复物品和一种状态效果做完整，明确攻击距离、遮挡、冷却、弹药或 MP 消耗及命中时机。优先保证玩家与怪物的伤害、死亡、遗物和断线处理一致。

补充跨图、开菜单、对话、死亡和重连交错时的检查。已有断线保存、自动重连、切图取消任务和旧地图攻击失效机制应继续使用，再补齐对局身份与旧交互回复校验，避免迟到的上一段对话或上一局操作作用于当前角色。

第二阶段不以完整还原全部 72 个工具定义为验收目标；每种选入正式测试局的技能都要有明确的行为测试。

### 禁区与世界事件

把当前单地图开发禁区提升为局级计划：服务端控制预警、生效、伤害、出口封闭和最终时限。即使地图暂时没人、玩家打开菜单或断开连接，局时钟仍推进。

加入一个可被多人共同改变的世界事件，例如重启电力装置后开放特殊出口。它需要同时改变相关地图上的可见状态和通行条件，而不是仅给所有人弹出相同文字。

本轮先以整张区域地图作为禁区单位。地图内局部禁区可作为后续扩展，避免同时实现两套未验证的范围规则。

### 两条逃生路线与结算

普通路线和特殊路线分别记录条件、所需物品、是否消耗、出口是否共用，以及个人离场结果。失败结果至少区分死亡、超时与退赛。结局先用现有图标与文字呈现，不需要制作专门 CG。

通过两条不同条件链验证多路线结局系统；完整剧情分支和正式文案以后继续扩写。

### 现有测试内容需要修正的地方

- Map024 事件 1–5 使用门图片，但事件命令为空，没有钥匙门逻辑。
- Map024 事件 7 发放 2000 金币，没有自开关或消除逻辑，可重复领取；它不是局内只可搜刮一次的共享箱子。
- Map024 事件 8 是旧装备耐久变量的修复测试；事件 13 是可重复恢复事件，都不能直接作为平衡后的正式局内服务。
- Enemy22 的掉落 Item27 是分类标题，Enemy23 的掉落 Item26 未命名，需要替换为有效测试掉落。
- Item44 的恢复效果重复写了两次 HP 全恢复，没有 MP 恢复；应明确本轮所需效果。
- 部分关键物品类型条目实际是合成材料。当前没有可直接复用的完整钥匙出口与胜利结算链。
- 仓库当前没有 `audio/bgm/` 与 `img/pictures/`。Map030 引用的 `PerituneMaterial_WildField_loop` 背景音乐缺失；恢复这首原曲的表现时才需要补文件，不妨碍无 BGM 的玩法验证。

新增钥匙、零件或出口状态可以先复用现有图标和事件图片，由开发补充测试配置。无需为了这些占位内容采购新美术。

## 你需要准备什么

### 推进当前 MV 原型不需要补充素材

上述地图、人物、道具图标、怪物和音效已足够。下一步可直接由开发整理场景配置、复制必要测试页、添加规则与回归案例。用户不需要重新上传整个素材库，也不必预先制作大世界地图。

真正有帮助的是一份简短的规则偏好：死亡掉落哪些东西、退出与重连怎么算、个人逃生后是否继续旁观、出口是个人开启还是全局共享、钥匙是否消耗，以及第二条逃生路线想表达什么。没有这些偏好时，可以先按本文可调整的测试规则实现，再通过试玩确定。

如希望自己用 RPG Maker 编排测试内容，可准备一张小型回归地图，集中摆放个人对话、共享门、两个箱子、条件出现的怪物和两个传送点。等个人与共享标记规范明确后再填写相应标记，避免先按旧全局变量写一整套联网事件。该地图也可以由开发创建。

### 只有特定兼容目标需要额外样例

| 目标 | 最小样例 | 是否阻塞上述 MV 完整回合 |
| --- | --- | --- |
| 验证实际 MZ 格式 | 由目标 MZ 版本保存的最小工程，含 `System.json`、`Tilesets.json`、`MapInfos.json`、一张地图、它引用的数据库条目与素材，以及事件预期行为；说明版本。若用非标准图块尺寸，应实际放进样例 | 不阻塞；要宣称支持该 MZ 版本时必须补 |
| MZ Effekseer | 一条实际动画数据、对应效果文件及引用贴图，说明如何触发与预期画面 | 不阻塞；现有 MV 图像帧动画不能证明它兼容 |
| 特定插件行为 | 只含相关插件及依赖、参数、一个最小事件页与必需素材的工程，并说明操作步骤和预期结果 | 仅当下一版必须包含该行为时需要 |
| 特殊人物表、加密素材或其他布局 | 一个实际文件、其约定或使用它的最小工程，以及预期展示方式 | 标准素材测试不需要 |
| 恢复缺失音乐或演出图片 | 原文件及其在事件／数据库中的名称对应关系，优先只补实际要验证的一项 | 不阻塞；可先静音并用文字结算 |

不必一次准备全部兼容包。先提交想优先验证的一种；插件名称或截图只能帮助说明目标，不能替代格式和行为测试样例。

大地图与更多玩家的负载测试由开发使用现有图块生成或拼接测试内容、复制实例并驱动机器人完成。最终世界布局与容量仍需后续独立验证，无需现在通过增加美术数量来模拟服务器压力。

## 验收清单

| 场景 | 必须观察到的结果 |
| --- | --- |
| 两局使用同一源地图 | 人物、掉落、箱子、开关和怪物完全隔离，旧局请求不能操作新局 |
| 两人同时搜刮最后一件物品 | 只产生一次成功；失败或重试不复制资源 |
| 打开菜单、对话或后台切换 | 其他人、世界时钟、禁区和自身受伤继续由服务端推进 |
| 个人与共享事件并存 | 个人选择不改别人进度；共享门的画面与碰撞对所有参与者一致 |
| 条件敌人切换页面 | 未激活时既不可见也不能攻击或受击；激活后的 HP 与存在性一致 |
| 搜刮、合成时切图或死亡 | 无远程领物、重复扣除或未提交奖励；动作的中断与结果明确 |
| 断线重连 | 回到同一局同一角色，不能清洗伤害、死亡、禁区状态或库存 |
| 对话取消与旧回复到达 | 旧回复不能推动新事件或上一局的事件 |
| 两条逃生路线 | 各自检查条件、消耗与出口状态，分别产生正确且仅一次的结局 |
| 连续开新局 | 不需要管理员修状态；旧局资源、计时器和交互不泄漏 |
| 服务意外重启 | 局状态明确中止或按约定处理，已提交结果不会重复发放 |

延迟与重复请求可以在应用协议测试中注入；真实 WebSocket 已提供有序传输，网络丢包主要体现为重传、延迟和断线，不应将其简化成随意打乱同一连接的数据帧。需要分别测试实际断线、跨连接迟到动作、重试以及 HTTP 地图载入竞态。

记录 tick 耗时、状态更新延迟、数据库事务耗时、任务积压和资源结算结果。通过这些检查后，再扩大人数与世界规模；自建远端编辑器、全面插件兼容、多进程分区、长期世界恢复与正式内容量作为后续阶段推进。
